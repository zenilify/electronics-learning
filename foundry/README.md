# Kaizen Firmware Foundry

Reproducible cloud builds for the whole microcontroller fleet: one command builds
every ESPHome node, the bare ESP-IDF StickS3 bridge, the Wio Terminal and M5 Arduino
sketches, the PaperS3 badge (PlatformIO) and an Apache NuttX "TabOS" spike for the
Tab5. Everything runs in Google Cloud Build in GCP project `papps-513907` (PAPPS).
Born in the 2026-11 GCP credit sprint (lane C).

> **Lesson-style summary.** Your firmware used to build only on the machine that
> had the right toolchain installed (estudio for the StickS3, the macbook for the
> Wio, cachy for ESPHome). The foundry puts each toolchain in a pinned container
> image, so any machine with `gcloud` can rebuild all of it identically, and every
> build leaves a manifest (sha256, size, versions) next to the binaries.

## How to run it

```bash
# from the electronics-learning clone (macbook/estudio); gcloud runs on cachy
GCLOUD_HOST=cachy foundry/submit.sh images           # only when a pin changes
GCLOUD_HOST=cachy foundry/submit.sh firmware          # the full matrix
GCLOUD_HOST=cachy foundry/submit.sh firmware "nuttx"  # one family (esphome idf arduino nuttx qemu)
```

1. `stage.sh` copies **git-tracked files only** from the four clones into
   `/tmp/kaizen-foundry-ctx/src/` (plus the generated, untracked PaperS3 `screens.h`,
   recorded by sha256) and writes `sources.tsv` (commit + dirty count per repo).
2. A **secret gate** refuses to continue if a `secrets.yaml`, `secrets.h`,
   `sdkconfig.credentials`, `*.token`, `.env`, key file, or a credential-shaped
   string (Tailscale, GitHub, Google key, PEM private key) is in the context.
3. Cloud Build (e2-highcpu-32) runs the five families in parallel. Each target writes
   `status.json` + `build.log`; failures never stop the other targets.
4. `manifest.py` writes `manifest.json` / `manifest.md`; everything is uploaded to
   `gs://papps-c-foundry/<YYYY-MM-DD>/<target>/`. The build is marked FAILURE if any
   target failed (the artifacts are still uploaded first).

## Secrets: placeholders only

Real credentials never leave the fleet. `scripts/dummy_secrets.py` generates a
`secrets.yaml` for every `!secret` key the configs use, and a `secrets.h` from
`secrets.h.example`. Values are deterministic and say `foundry` (`foundry-dummy-ssid`,
32-byte base64 API keys derived from the key name). **The binaries cannot join any
real network — they prove the code compiles; do not flash them as-is.**

## TabOS spike — NuttX on the Tab5

Upstream NuttX already has a board port, `boards/risc-v/esp32p4/esp32p4-tab5`
(configs `nsh`, `lvgl_demo`, `lvgl_term`, `python`, `sdmmc_spi`). It brings up
USB-Serial-JTAG console, I2C0, 32 MB PSRAM, GPIO/BOOT, both PI4IOE5V6408 expanders,
MIPI-DSI with the ST7121/ST7123 (and ILI9881C) panels and touch.

**Missing upstream — candidate contributions** (from the board's own docs):

| Peripheral | Part | Why it matters for "TabOS" |
|---|---|---|
| Wi-Fi / BLE / Thread | ESP32-C6 over SDIO2 (esp-hosted) | no network at all without it — the biggest gap |
| Audio out / in | ES8388 codec + NS4150B amp, ES7210 mic array | voice assistant role |
| Camera | SC2356 MIPI-CSI | QR / vision |
| Battery monitor | INA226 (5 mΩ shunt) | battery % on screen |
| RTC | RX8130CE | wall clock without network |
| microSD | SDMMC slot (only SPI mode via `sdmmc_spi` today) | storage |
| IMU | BMI270 | not listed as supported either |

The ESP32-C6 hosted link is the natural first contribution: it unlocks networking and
is shared by every ESP32-P4 board with a C6 companion.

## Cost and cleanup

Runs are billed per build-minute (e2-highcpu-32). Storage is small: builder images in
Artifact Registry `us-central1/kaizen-foundry` and binaries in `gs://papps-c-foundry`.
Source uploads live in `gs://papps-c-foundry/_source/` and can be deleted any time.
Measured numbers per run are in `RESULTS.md`.
